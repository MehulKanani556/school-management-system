1. Platform Overview

This is a multi-tenant SaaS School Management System that supports multiple schools on a single platform. Each school operates in isolation under its own subdomain, managed by a School Admin. A Super Admin oversees the entire platform.

Architecture: React SPA frontend → REST API (Express.js) → MongoDB (Mongoose ODM) + Socket.IO for real-time features. JWT-based authentication with role-based access control.

Platform Scope

  • Multi-school support with school-level data isolation
  • 8 distinct user roles with granular permissions
  • 20+ functional modules covering all school operations
  • Real-time GPS tracking, messaging, and notifications
  • File uploads (photos, assignments, books, reports)
  • PDF generation (report cards, fee receipts, payslips)
  • CSV import/export for bulk data operations
  • Email notifications (OTP, fee reminders)

3. User Roles & Permissions

Super_Admin Super Admin

Platform owner. Manages all schools, global settings, revenue, security, backups, and platform-wide analytics. Not tied to any school.

School_Admin School Admin

Manages a single school. Controls students, teachers, classes, fees, exams, attendance, timetables, payroll, admissions, transport, library, and all school-level operations.

Teacher Teacher

Handles assigned classes. Marks attendance, adds exam marks, uploads assignments, creates quizzes, logs behavior, schedules PTM meetings, manages lesson plans and resources.

Student Student

Views own academic data. Checks attendance, results, assignments, timetable, fees, exams, library books, and takes quizzes. Logs in with admission number.

Parent Parent

Monitors child's academic progress. Views attendance, results, fees, assignments, exams, behavior logs, PTM meetings, and transport status. Can pay fees online.

Accountant Accountant

Manages all financial operations. Collects fees, generates payroll, creates fee structures, produces financial reports, and maintains audit logs.

Librarian Librarian

Manages library operations. Maintains book inventory, issues/returns books, tracks reservations, collects fines, and manages circulation history.

Transport_Manager Transport Manager

Manages school transport. Maintains vehicles, routes, drivers, trip logs, student assignments, and real-time GPS tracking.

4. Authentication Flow

Standard Login (All roles except Student)

1
User visits /login and enters email + password
2
Backend checks AUTO_LOCK_ACCOUNTS system setting. If account is locked (5 failed attempts), returns 423 error with 30-min lockout message
3
Password compared with bcrypt hash. On failure, increments failedLoginAttempts. At 5 failures, sets lockUntil = now + 30min
4
On success: resets failed attempts, generates JWT access token (7d) + refresh token (7d)
5
Tokens stored in httpOnly secure cookies + returned in response body
6
Frontend stores user in Redux + persists via redux-persist
7
Role-based redirect: School_Admin → /school-admin, Teacher → /teacher, Student → /student, etc.

Student Login (Special Flow)

1
Student enters Admission Number + password (not email)
2
Backend queries Student model by admissionNumber, populates classSection and schoolId
3
JWT generated with role = 'Student', redirected to /student dashboard

Forgot Password Flow

1
User submits email at /forgot-password
2
4-digit OTP generated, saved to user record, emailed via Nodemailer/Gmail
3
User enters OTP at /verify-otp — OTP cleared on success
4
User sets new password at /reset-password — bcrypt hashed and saved

Route Protection

  • auth middleware: Verifies JWT, loads user from DB (Student or User model based on role)
  • requireRole(...roles): Checks req.user.role against allowed roles, returns 403 if denied
  • RoleRoute (frontend): React component that redirects unauthenticated users to /login and wrong-role users to /
  • checkMaintenance: Applied to all routes — blocks access during maintenance mode

13. Core Module Workflows

Admission Workflow

1
Enquiry received (walk-in, online, referral, social media, advertisement)
2
School Admin creates enquiry record with student/parent info and standard applied
3
Status set to "Enquired" → follow-up scheduled → status updated to "Follow-up"
4
Decision made: "Admitted" or "Rejected" or "Withdrawn"
5
On admission: enroll student → Student record created with auto-generated admission number (ADM-YYYY-NNN)
6
Student assigned to class section, parent account linked

Exam & Marks Workflow

1
School Admin creates exam: name, type (unit_test/midterm/final), date, maxMarks, class
2
Exam remains unpublished (not visible to students/parents)
3
Teacher adds marks for each student after exam
4
Admin toggles "Publish" → results now visible to students and parents
5
Students view results, parents monitor performance, analytics generated
6
Report card generated with grading scale (configured in school settings)

Fee Management Workflow

1
Accountant/Admin creates fee structure: category (tuition/transport/library), amount, per standard
2
Apply fee structure to standard → FeePayment records created for all students (status: pending)
3
Accountant collects fee: enters paid amount, method, transaction ID
4
System calculates: totalAmount = amount - discount + lateFees
5
Status updated: pending → paid / partially_paid / overdue
6
School revenue auto-synced via MongoDB post-save hook
7
Fee receipt PDF generated and downloadable by student/parent/accountant

Assignment & Submission Workflow

1
Teacher uploads assignment: title, description, subject, file attachment, due date
2
Students in the class section receive notification
3
Student submits file before due date → status: "Submitted"
4
Late submission → status: "Late"
5
Teacher reviews submissions, assigns marks and feedback → status: "Graded"
6
Student views grade and feedback

Quiz Workflow

1
Teacher adds questions to question bank (by subject/topic)
2
Teacher creates quiz: title, subject, class, duration (minutes), passing score (%)
3
Selects questions from bank or auto-generates exam paper
4
Publishes quiz → visible to students
5
Student takes quiz within time limit, submits answers
6
Score calculated, attempt recorded, teacher views all attempts

Leave & Payroll Workflow

1
Teacher applies for leave: type, start/end date, reason
2
School Admin reviews and approves/rejects leave request
3
Accountant generates monthly payroll (bulk or single): basic salary, bonus, deductions
4
Net salary = basicSalary + bonus - deductions
5
Accountant processes payroll: marks as paid, records payment method and transaction ID
6
Teacher downloads payslip PDF

Student Promotion Workflow

1
At end of academic year, admin reviews student performance
2
Admin runs "Promote Students" for a standard
3
Students moved to next standard/class section
4
Promotion history recorded (PromotionHistory model)
5
New academic year created for next session

14. Real-Time Features (Socket.IO)

EventDirectionDescription
register_userClient → ServerUser joins private room (userId) on login
send_direct_messageClient → ServerSend message: saved to DB, emitted to recipient's room
new_direct_messageServer → ClientReceive real-time message (both sender and recipient)
subscribe_to_vehicleClient → ServerJoin vehicle room to receive GPS updates
update_vehicle_locationClient → ServerDriver/GPS device sends lat/lng update
vehicle_location_updatedServer → ClientBroadcast location to all vehicle subscribers
subscribe_to_fleetClient → ServerJoin fleet_management room (transport manager)
fleet_initServer → ClientSend all known vehicle locations on subscription
fleet_location_updatedServer → ClientBroadcast any vehicle update to fleet managers
disconnectClient → ServerClean up user socket mapping
Vehicle Location Cache: Server maintains an in-memory vehicleLocationMap (vehicleId → {lat, lng, updatedAt}). New subscribers immediately receive the last known location without waiting for the next update.

16. Security Architecture

  • JWT Authentication: Access + refresh tokens (7-day expiry), stored in httpOnly secure cookies with sameSite: Strict
  • Password Hashing: bcrypt with salt rounds (10)
  • Account Lockout: 5 failed attempts → 30-minute lockout (configurable via AUTO_LOCK_ACCOUNTS setting)
  • Role-Based Access Control: requireRole middleware on every protected route
  • Maintenance Mode: checkMaintenance middleware blocks all routes when enabled
  • Registration Control: GLOBAL_REGISTRATION setting can disable public signup
  • OTP Password Reset: 4-digit OTP via email, single-use (cleared after verification)
  • Audit Logging: All significant admin actions logged to AuditLog model
  • Multi-tenant Isolation: All queries scoped by schoolId to prevent cross-school data access
  • File Upload Security: Multer middleware with file type validation
  • Token Refresh: /generatenewtoken endpoint for seamless session renewal
