Fee Payment Verification — feeId Extraction Fragile

back/controllers/parent.controller.js — verifyFeePayment() — Line ~340

The orderId format is ORDER-{feeId}-{timestamp}. The verification extracts feeId with orderId.split('-')[1]. But MongoDB ObjectIds contain hyphens when converted to string in some formats, and the split index is fragile. If the format ever changes, fee payments will silently fail to update.

// FRAGILE: Assumes feeId is always at index [1] const feeId = orderId.split('-')[1]; // orderId = "ORDER-507f1f77bcf86cd799439011-1711234567890" // split('-') = ["ORDER", "507f1f77bcf86cd799439011", "1711234567890"] // [1] = "507f1f77bcf86cd799439011" ← works only if ObjectId has no hyphens
// FIX: Use a more robust extraction const parts = orderId.split('-'); const feeId = parts.slice(1, -1).join('-'); // handles ObjectIds with hyphens
🟠 High — Online fee payment verification may silently fail

Fee Revenue Sync — Double-Counting on Partial Payments

back/models/feePayment.model.js — post('save') hook & back/controllers/accountant.controller.js — collectFee()

The FeePayment post-save hook recalculates total revenue by summing ALL paid fees. But the accountant controller ALSO does School.findByIdAndUpdate(schoolId, { $inc: { revenue: diff } }) after saving. This means revenue is incremented twice — once by the controller and once by the post-save hook recalculation. Over time, the school revenue figure becomes incorrect.

// BUG: Revenue updated twice // 1. Controller: $inc revenue by diff await School.findByIdAndUpdate(schoolId, { $inc: { revenue: diff } }); // 2. Post-save hook: recalculates and overwrites with aggregate sum // These two operations conflict — the $inc is overwritten by the aggregate
🟠 High — School revenue figure is unreliable

Quiz Score Calculation — Frontend Uses Count, Backend Uses Points

front/src/pages/Student/ELearning.js vs back/controllers/student.controller.js — submitQuiz()

The frontend calculates score as score / selectedQuiz.questions.length (count-based), but the backend calculates it as score / totalPoints (points-based, where each question has a points value). The displayed accuracy percentage on the results screen is different from what's stored in the database.

// Frontend: count-based Math.round((score / selectedQuiz.questions.length) * 100) // e.g., 3/5 = 60% // Backend: points-based const percentage = totalPoints > 0 ? (score / totalPoints) * 100 : 0; // e.g., 30/50 = 60% (different)
⚪ Medium — Quiz score display inconsistent between UI and stored data

Transport Fee — Upsert Uses Wrong Match Condition

back/controllers/transport.controller.js — assignStudent() — Line ~130

When a student is assigned to a transport route, a fee is auto-created using findOneAndUpdate with status: { $ne: 'paid' } in the match. If the student already has a paid transport fee, a NEW fee record is created (upsert). This can result in duplicate transport fee records for the same student and year.

// BUG: Creates duplicate if existing fee is paid await FeePayment.findOneAndUpdate( { studentId, category: 'Transport', academicYear, status: { $ne: 'paid' } }, { ... }, { upsert: true } // ← creates new record if paid one exists
// FIX: Remove status from match, use findOne first to check const existing = await FeePayment.findOne({ studentId, category: 'Transport', academicYear }); if (!existing) await FeePayment.create({ ... });
⚪ Medium — Duplicate transport fee records possible

The payroll notification uses type: 'Payroll', but the Notification model's type enum only allows: 'Assignment', 'Mark', 'Attendance', 'Fee', 'Announcement', 'Leave', 'General'. The notification creation will fail Mongoose validation and throw an error, which is caught silently.

// BUG: 'Payroll' not in enum await nc.sendNotification({ type: 'Payroll', ... }); // Notification model enum: ['Assignment','Mark','Attendance','Fee','Announcement','Leave','General'] // 'Payroll' is not listed → Mongoose validation error → notification silently fails
// FIX: Use 'General' or add 'Payroll' to the enum await nc.sendNotification({ type: 'General', ... }); // OR add 'Payroll' to notification.model.js enum
⚪ Medium — Payroll notifications silently fail due to enum mismatch
